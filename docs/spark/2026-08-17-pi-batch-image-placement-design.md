# Pi 批量图片提交、自动排图与持久保存设计

日期：2026-08-17  
状态：Owner 已确认产品方向，书面规格已自检，待 Owner 复核  
任务：WMB-5307  
范围：在当前创作项目的 Pi 输入框提交 1–10 张图片，由 Pi 理解图片和正文、选择合理位置并自动保存新的核心正文版本；全部原图妥善保存在当前项目素材中。

## 1. 决策摘要

Owner 可以在当前创作项目的 Pi 输入框中选择或拖入 1–10 张 PNG、JPEG、WebP 或 GIF，并附带自然语言要求。发送后，WMB 必须先把整批原图持久导入当前项目，再允许 Pi 分析图片与当前最新版正文。Pi 为适合正文的图片选择语义相关位置，生成 alt、图注、宽度与对齐，随后通过既有核心正文版本协议自动保存一个新版本。

旧正文版本不得被覆盖。未采用图片仍属于当前项目素材，必须保留“本批次未采用”状态及原因。任何导入、视觉分析、版本冲突或保存失败都不得显示为排图成功。该能力只改变核心正文和项目素材，不进行平台适配或发布。

选定方案是“Pi 输入框直接提交”，不新增一个必须先经过的独立素材库页面，也不增加保存前布局确认板。保存后的 Studio 已提供图片拖拽、上移、下移、尺寸、对齐与图注能力，Owner 可继续微调。

## 2. 用户主流程

1. Owner 打开一个明确的创作项目，Pi 当前焦点指向该项目。
2. Owner 点击 Pi 输入框的图片按钮，或把图片拖入输入区域。
3. 输入框上方显示有序附件队列：缩略图、文件名、尺寸或读取状态，以及单张移除动作。
4. 队列最多 10 张；Owner 可以输入要求，例如“把这些配图放到最能帮助理解的位置，不合适的不要硬塞”。
5. Owner 发送消息。发送动作冻结本次附件清单、顺序、项目 ID、当前核心版本 ID 和 revision，形成一次稳定批次。
6. WMB 逐张校验并导入原图。只有全部输入都得到明确导入结果后，才启动 Pi 排图任务。
7. Pi 读取冻结的用户消息、最新版正文、现有图片引用与绑定，以及本批次所有已保存图片的可视内容。
8. Pi 对每张图片给出 `used` 或 `unused` 决策；`used` 图片包含插入锚点、alt、图注、宽度和对齐，`unused` 图片包含简短原因。
9. Pi 生成完整目标正文和完整 `mediaBindings`，使用发送时冻结的 expected revision 保存一个新核心版本。
10. WMB 回读项目，确认新版本、正文图片 token、绑定及批次结果一致，才显示“已完成排图并保存新版本”。
11. Studio 展示新版本；Owner 可以继续拖动或使用图片工具条微调，再按既有流程保存后续版本。

## 3. 交互设计

### 3.1 Pi 输入框附件队列

复用现有 `PiComposer` 中已存在但禁用的“插入图片”入口，将其改为真实选择入口。图片也可直接拖入 composer。普通文件附件按钮不在本任务中启用。

附件队列必须：

- 位于消息输入区域内，但不覆盖正文 textarea、模型菜单或发送按钮；
- 保持用户选择顺序；
- 每张图片显示缩略图、可读文件名、读取/就绪/失败状态和移除按钮；
- 在发送前只持有 renderer 内的待提交对象，不提前冒充项目素材；
- 达到 10 张时阻止继续添加并说明上限；
- 相同文件可被识别为重复内容，但是否复用由持久层哈希规则决定，UI 不猜测；
- 支持键盘聚焦、移除和发送；
- 在 1100px 最小窗口下不产生页面横向溢出。

发送进行中，当前批次变为不可编辑。新的用户输入继续遵循现有 Pi `steer` / `followUp` 语义，但不得改变已冻结批次。

### 3.2 对话结果

Pi 最终消息只报告用户需要知道的结果：

- 已保存的新核心版本；
- 已采用图片数量；
- 未采用图片数量及逐张简短原因；
- 若失败，明确失败阶段和可恢复动作。

不得把内部 asset ID、grant、lease、Base64、数据库字段或工具调用流水作为默认用户文案。

## 4. 组件与职责边界

### 4.1 `PiComposer` 附件采集

职责：选择、拖入、预览、排序、移除 1–10 张本地图片，并随消息提交稳定附件描述。

不负责：写入项目素材、调用视觉模型、修改正文或决定图片位置。

### 4.2 renderer → preload 附件提交边界

扩展 Pi 发送输入，使一次消息可以携带结构化图片附件，而不是把本地路径拼入消息文本。边界只接受允许的图片类型和有界字节载荷；不得把任意文件系统路径暴露给 Pi。

消息文本和附件必须共享同一个提交动作及批次身份。现有纯文本发送调用方保持无附件时的原行为。

### 4.3 主进程批次编排

新增一个有持久状态的项目图片批次，负责：

- 冻结 `workspaceId`、`projectId`、消息、附件顺序、基线版本与 revision；
- 逐张调用既有资产导入能力或其同源领域函数；
- 保存每张附件的导入结果和最终采用决策；
- 全部原图持久化后创建 Pi 工作输入；
- 管理 `importing → analyzing → saving → completed` 主链；
- 如实进入 `failed` 或 `conflicted`，并支持同一批次安全恢复；
- 对同一请求和规范化输入保持幂等。

批次是运行与追溯对象，不替代 `assets`、`content_project_assets` 或核心正文版本的权威归属。

### 4.4 项目素材存储

复用现有资产存储、内容寻址/哈希复用和 `content_project_assets` 关联。每张原图必须先成为稳定 asset，再进入 Pi 排图。

为了让未采用语义可追溯，批次附件记录至少表达：

- 批次 ID、顺序、asset ID；
- 原始文件名、MIME、宽高、字节数和内容哈希；
- `pending | used | unused` 决策；
- 未采用原因；
- 对应新核心版本 ID（成功时）；
- 创建与完成时间。

原图是权威素材。缩略图或后续裁切是派生物，不得覆盖原图。

### 4.5 Pi 排图执行器

Pi 输入必须包含：

- 精确 project ID；
- 基线核心版本 ID 和 revision；
- 完整正文；
- 正文内现有 `wmb-asset://` 图片及 `mediaBindings`；
- 本批次图片的稳定 asset 引用、顺序和视觉内容；
- Owner 消息；
- 明确的输出及保存约束。

Pi 必须按文章语义决定位置，而不是机械平均分布。首图只在图片适合作为文章入口时使用；正文图应置于其能解释或强化的段落之后。图片无关、重复、信息错误、可读性不足或会误导时应标记未采用，禁止为了用完素材而强插。

Pi 只能通过受控项目图片导入与核心版本保存能力写入。不得直接访问任意路径，不得创建平台版本，不得发布。

### 4.6 核心版本保存

保存沿用 `wmb_save_core_version` 的完整版本语义：

- 传入基线 expected revision；
- body 是完整目标 Markdown；
- 每个正文图片 occurrence 都有一致的 `mediaBindings`；
- 本批次图片的 alt、caption、widthPreset 和 align 一次提交；
- 保存成功后通过 `wmb_get_content` 回读确认。

自动保存产生新版本，不覆盖历史版本。若正文在排图期间改变，保存必须冲突而不是覆盖。

## 5. 图片放置规则

1. 保留正文原有标题、段落、列表、引用、代码块和现有图片顺序，除插入本批次图片所需的变化外不重写文章。
2. 图片 token 独占段落，不插入标题文本、代码围栏、表格单元或已有 Markdown token 内部。
3. 插入锚点以稳定的正文块语义描述，并在最终保存前解析为明确 Markdown offset；不得依赖暂态 DOM 节点身份。
4. 同一 asset 可出现多次，但每次 occurrence 的绑定独立；默认每张本批次图片最多采用一次。
5. 默认宽度根据图像用途选择：首图或横向概览可用 large/full，正文解释图优先 medium/large；不得因原图像素宽度撑破正文列。
6. 默认居中。只有图片内容和相邻排版明确适合时才使用左/右对齐。
7. alt 描述图片可见信息，不堆关键词；图注说明该图为什么出现在此处，不伪造来源、数字或结论。
8. 动图保留 GIF 原件；Pi 以可读取的代表帧理解内容，正文仍引用原始 asset。
9. 已存在的正文图片不因本批次排图丢失，其绑定按现有 occurrence 规则保持。

## 6. 状态、幂等与恢复

批次状态：

```text
queued
→ importing
→ analyzing
→ saving
→ completed
```

分支状态：

- `failed_import`：至少一张输入无法合法读取或持久保存；
- `failed_analysis`：原图已保存，但 Pi 未产生合法排图决策；
- `conflicted`：基线 revision 已过期；
- `failed_save`：排图结果存在，但核心版本未成功保存；
- `canceled`：Pi 开始前由 Owner 取消；开始后的停止沿用现有 Pi 停止语义，并保存真实终态。

每批次有稳定 request ID。相同 request ID 与相同规范化输入只回放既有结果；改变附件、顺序、消息或项目必须创建新请求。资产层继续以内容哈希复用相同原图，复用不得丢失本批次附件记录。

应用退出后：

- 已写入的 asset 和项目关联继续存在；
- `importing` 批次从持久记录判断每张导入结果，避免重复写入；
- `analyzing` 不伪装为仍在运行，按现有 Pi 运行恢复能力恢复或进入明确失败；
- `saving` 先按 request ID 查询既有回执，不能盲目再次保存；
- `completed` 必须能回读对应核心版本。

## 7. 失败处理

### 7.1 输入校验失败

不支持类型、空文件、解码失败、超过单文件安全限制或总数超过 10 时，在发送前指出具体图片。合法附件不被静默删除，Owner 可移除失败项后重新发送。

### 7.2 导入失败

整批不得启动 Pi。已成功导入的原图保留并关联项目，批次记录逐张结果。重试只处理尚未成功的附件。

### 7.3 视觉分析失败

原图全部保留，正文和版本不变。不得用文件名猜测图片内容后继续保存。

### 7.4 部分图片不适合

这不是失败。Pi 将其标记为 `unused` 并提供原因，其余图片继续排版。全部图片均不适合时，仍可完成批次，但不创建内容相同的空新版本；结果应说明原图已保存且正文未改变。

### 7.5 revision 冲突

不得覆盖新正文。保留已导入素材和排图决策，将批次标记为 `conflicted`。恢复动作基于最新正文创建新的分析/保存尝试，而不是篡改旧批次基线。

### 7.6 保存或回读失败

不得报告完成。若命令回执显示保存已发生但回读暂时失败，保持可判定状态并按相同 request ID回查，禁止自动创建第二个版本。

## 8. 权限与安全边界

- Pi 附件发送属于 Owner 在当前创作项目内明确发起的内容协作动作，可签发最小 `content.save_version` 范围 grant；Agent 不自行扩大权限。
- 图片导入沿用 `wmb_import_project_image` 的 authority、lease、request ID 和回执规则。
- renderer 不把任意本地路径、凭据或超出批次的文件暴露给 Pi。
- SVG 不属于本次 Pi 输入框批量选择范围；现有受限 SVG 工具能力不删除，但 UI 主流程只接受 PNG/JPEG/WebP/GIF。
- 不自动生成平台版本，不调用发布适配器，不改变最终发布必须由 Owner 手动完成的边界。
- 不修改 foundation 品牌 token；新增 UI 复用现有设计变量。

## 9. 明确不做

- 不启用通用文件附件按钮；
- 不建立独立图片管理产品或跨项目全局图库；
- 不在保存前增加强制布局审批板；
- 不让 Pi 自动修图、裁切、生成图片或删除素材；
- 不改写整篇文章以迁就图片；
- 不自动适配小红书、公众号或 X；
- 不自动发布；
- 不为超过 10 张图片设计后台大批量导入流程；
- 不改变品牌级颜色、字体、topbar 或核心 surface token。

## 10. 可证伪验收

1. 当前创作项目的 Pi 输入框可选择或拖入 1–10 张 PNG、JPEG、WebP、GIF，并显示有序缩略图队列。
2. Owner 可在发送前移除任意单张图片；纯文本消息保持原行为。
3. 发送后全部合法原图先进入持久 asset 存储并关联准确 project ID，重启后仍可回读。
4. Pi 实际读取图片视觉内容、当前正文、现有图片与 Owner 消息，不以文件名代替视觉分析。
5. Pi 对每张图片产生 `used` 或 `unused` 决策；未采用图片保留在项目素材中并可回读原因。
6. 合适图片插入语义相关正文块附近，图片 token 不破坏标题、代码围栏、表格或既有 Markdown 结构。
7. 自动保存一个新的核心正文版本；旧版本保持不变。
8. 新版本中每个图片 token 与 `mediaBindings` 的 `(assetId, occurrence)` 一一对应。
9. 保存并重载后，图片顺序、alt、图注、宽度和对齐保持；现有图片绑定不串位。
10. 相同批次重试不会重复存储相同资产，也不会重复创建同一正文版本。
11. 导入失败、Pi 分析失败、保存失败和 revision 冲突均不产生伪成功；正文保持未被错误覆盖。
12. 真实 Electron 场景覆盖：多图提交、至少一图采用、至少一图未采用、自动保存、重载、素材回读、版本冲突和失败恢复。
13. 1100×800 下附件队列、Pi 输入框、Studio 文档列无横向溢出，page error 为 0，键盘路径可达。
14. 设计 token drift gate 继续通过，且未修改 foundation 品牌 token。
15. 平台版本与发布记录保持不变。

## 11. 目标测试边界

实现应提供能够阻止以下回归的聚焦合同或行为测试：

- composer 附件上限、类型、移除和纯文本兼容；
- 批次冻结、逐张导入状态与哈希复用；
- Pi 输入包含正文和稳定资产，不包含任意本地路径；
- 合法排图输出校验及 Markdown/绑定一致性；
- expected revision 冲突不覆盖；
- 同 request ID 幂等回放；
- 已导入但未采用图片持久回读；
- 应用重启后的中间状态恢复。

最终使用一个真实 Electron 聚焦场景证明完整用户链，不以 DOM 假数据、直接数据库造终态或仅测试工具函数代替真实发送与保存。

## 12. 实施范围

允许修改：

- Pi composer 及其样式；
- renderer/preload/main 的 Pi 消息附件协议；
- 项目图片批次持久状态及必要 migration；
- 既有项目图片导入、核心版本保存编排的复用入口；
- Pi prompt/tool 输入；
- Studio 项目素材读模型中未采用状态的必要展示；
- 聚焦测试与本任务证据。

保护范围：发布协议、平台适配、来源 SSOT、调查状态机、角色权限总体模型、依赖与 foundation 品牌 token。

本设计应作为一个实施任务完成。若实现发现必须新增跨项目图库、通用附件系统、图片生成服务或新的发布生命周期，应停止并作为新增范围呈报，不得吞入 WMB-5307。
