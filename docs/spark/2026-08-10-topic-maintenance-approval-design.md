# 主题整理提案与主管审批闭环（Design draft；2026-08-10 主管授权翻转修订）

- 日期：2026-08-10
- 路由：Design（角色默认职责 + 内部审批边界变化）
- 状态：Owner locked（2026-08-10 历史 lock 保留；2026-08-10 主管授权翻转修订已并入，见 §4/§6/§7 注记）；施工仍须 `TASKS.md doing`
- 触发事实：Owner 要求合并重复主题时，桌助最终要求 Owner 到前端手工处理；真实会话显示资料员只能改资料归属，无法完整合并主题，策划工单又固定为 `daily_judge`。
- 对齐：`PRODUCT.md` C1/C3/C6/C8、`PRD.md` §2.0/§2.3、`SPEC.md` §1.0/§1.1/CAP-003、`docs/spark/2026-08-07-role-permission-design.md`、`docs/spark/2026-08-10-supervisor-authority-design.md`（主管授权翻转）

## 1. 结论

主题应由 Agent 整理、人审批，不应由 Owner 自己到主题页完成员工工作。

```text
资料员检查主题家底
  → 形成一份主题整理提案（完整 before/after）
  → 桌助呈报
  → Owner 批准或驳回
  → 批准后整批原子生效并读回
```

职责保持分离：

- **策划**：判断哪些长期线值得跟、给出新主题候选；不负责日常去重、改名、合并和归档整理。
- **资料员**：主题家底维护人；盘点重复/混乱主题并提交可审批的整理提案。
- **桌助**：派工、呈报状态与结果；不得代批，不得把执行退回给 Owner 手工操作。
- **Owner**：只批/驳回准确提案；批准是生效边界。

## 2. 当前断点（已证实）

1. `cap.library_organize` 只给资料员 `knowledge.record_batch`，能把资料挂到主题，却不能完整管理主题实体。
2. `knowledge.domain_create/update` 虽登记在策划的 `cap.knowledge_curate`，Pi 侧没有对应可操作包装；桌助真实会话因此把删除旧主题、改绑历史对象退给 Owner UI。
3. `wmb_spawn_job(planner)` 固定映射到 `daily_judge`；其策略只生成当日方案，成功读回也只认 `plans.save`，不是主题维护工单。
4. 现有资料员工单成功读回只认资料变更，无法证明一个主题整理批次已经完整提出或生效。

因此，“策划在注册表里有主题写命令”不等于“产品存在可派、可批、可验收的主题管理流程”。

## 3. 最小产品合同

### 3.1 提案范围

一份主题整理提案可以包含以下动作的有序集合：

- 新建主题；
- 修改主题名称、说明或状态；
- 合并重复主题：选择保留主题，把被合并主题关联的资料、选题、内容项目、复盘等正式关系迁移到保留主题，再归档被合并主题；
- 调整资料与主题的归属；
- 将无效主题归档。

不包含硬删除。被合并主题保留审计身份并进入归档状态，避免历史引用断裂。

### 3.2 提案台账

主题页提供完整台账，今日页只投影需要 Owner 决策的待批摘要。每条提案至少展示：

- 提案标题、资料员工单与提出时间；
- 变更原因；
- 每个主题的 before/after；
- 将迁移的资料、选题、项目和复盘数量，可展开到准确 ID；
- 风险或不确定项；
- 状态：`proposed | approved | rejected | stale`；
- 提案 revision 与所有被触碰对象的 expected revision。

Owner 只需要“批准”或“驳回”；不是进入编辑表单替 Agent 收尾。

### 3.3 生效边界

- 资料员只能创建/修订 `proposed` 提案，不能应用提案。
- 提案生成前后，正式主题、关系和历史对象均不变化。
- Owner 批准绑定准确的提案 revision 与完整变更摘要。
- 应用在一个数据库事务内完成；任一对象 revision 过期则整批零写入，提案变为 `stale`，交回资料员重算。
- 成功必须读回：提案为 `approved`、全部目标关系已迁移、被合并主题已归档、无对象仍错误指向旧主题。
- 驳回只改变提案状态，不改变主题事实。

## 4. 授权形状（2026-08-10 主管授权翻转修订）

不把 `cap.knowledge_curate` 整包塞给资料员，也不开放权限配置 UI。

建议新增最窄能力：

- `cap.topic_maintain_propose`：资料员默认持有，只能读取主题家底并创建/修订主题整理提案。
- **提案应用命令（2026-08-10 翻转）**：`knowledge.topic_maintenance_approve / reject / reproposal_retry` 重分类为**仅主管可授予**——`agentGrantable:true`、`precise:false`、`defaultRoleBindings { desk: true }`、零员工绑定；资料员（仅 propose）、策划和外部 Agent 均不可调用（角色/执行边界拒绝，零业务写）。原「owner_ui 专属」表述由本修订取代（历史 Owner lock 记录保留，见 §7 修订注记）；四眼制衡保留：资料员提、主管批。

策划仍持选题判断能力。新主题候选若来自策划，也先成为待批提案，不直接绕过主管改正式主题结构。

## 5. 实现约束（Owner lock 后再拆任务）

1. 复用现有 `CommandReceiptV1`、revision、任务/角色过滤和 `suggested → confirmed/rejected` 状态模式；不造通用审批框架。
2. 主题提案是独立业务对象，不复用 `knowledge_suggestions` 表：后者强绑定 canvas 且只接受 node/relation，混用会污染两个领域。
3. 主题合并必须由一个领域命令完成全量关系迁移与归档；禁止资料员逐条调用现有工具拼出“看似合并”。
4. 资料员工单新增主题维护策略与专属读回；不能继续映射到只认资料变更的 `page_library` 成功条件。
5. 主管/资料员 Pi 工具与共享 `wemedia-buddy-operator` Skill 同步更新；主管遇到待批提案必须呈报与内部审批，禁止输出“请去前端自行整理”。
6. 实施前先修订 PRD/SPEC 与 canonical 角色设计，再登记 Capability、命令和任务合同；`TASKS.md doing` 仍是唯一施工许可。

## 6. 验收场景

以真实重复主题「Agent 工作流」与「Agent工作流方法」为最小可证伪场景：

1. Owner 对桌助说“合并这两个重复主题”。
2. 桌助派资料员；资料员产生一份提案，正式主题和关系保持原样。
3. 桌助向 Owner 呈现保留主题、迁移对象清单和被归档主题。
4. Owner 驳回：零主题业务写。
5. 再次提案并批准：一次事务完成全部迁移与归档，回读无遗留旧引用。
6. 在批准前并发修改任一目标主题：批准返回 stale，整批零写入。
7. 资料员、策划或外部 Agent 直接尝试应用提案：稳定返回角色/执行边界拒绝，零业务写（主管应用 = 正常路径，2026-08-10 翻转）。

## 7. Owner lock

1. 资料员是主题家底维护人：负责去重、改名、合并、归档和归属整理，但只能提交提案。
2. 策划负责长期线判断和新主题候选；任何 Agent 的主题结构变更都先进入同一待批台账。
3. Owner 批准后整批原子生效；批准前正式主题事实零变化。
4. 合并采用“迁移全部正式关系 + 归档旧主题”，不硬删除旧主题。
5. 主题页是完整提案台账；今日页只呈现待批摘要；桌助必须呈报，不得要求 Owner 手工完成整理。
6. 提案 stale 时整批零写入并退回资料员重算，不允许部分合并。
7. Non-goals：不做通用审批引擎、不做权限配置 UI、不自动批准、不改变选题/写作/发布角色边界。
8. Route: Design → Owner lock → PRD/SPEC/canonical role legislation → contracts + TASKS → implementation。

Owner lock 2026-08-10（用户自然语言原话构成有效授权，不要求口令）：

1. 「他应该有权利整理。」资料员负责主题家底整理。
2. 「整理完以后就像选题台账一样，会让我审批。」主题整理先形成待批台账，Owner 审批后才生效。
3. 「我批了就生效。」批准是唯一 Agent 提案生效边界，必须原子读回。
4. 「实施吧。」授权按本设计进入立法、任务合同与施工。
5. Owner 随后明确纠正：Owner 的自然语言实施指令本身有效，不得要求复制魔法口令。
6. 其余边界按本节 1-8：旧主题归档不硬删、stale 零写入、桌助必须呈报、不做通用审批引擎或权限配置 UI。

**§7 修订注记（2026-08-10 主管授权翻转，legislative）**：本节历史 Owner lock（2026-08-10 自然语言确认）保留为历史；依 `docs/spark/2026-08-10-supervisor-authority-design.md` §5/§8-4（Owner lock 2026-08-10 全 10 项），第 2/3 项中「Owner 审批/批准」修订为**主管（软件内 supervisor）审批**——主题整理应用命令 `agentGrantable:true`、`precise:false`、`{desk:true}`，仅主管可授予；资料员只 propose（四眼制衡保留）；「桌助必须呈报」修订为「主管负责内部审批与呈报」。红线定义不含内部审批（红线恰三类：最终发布、硬删执行、外部平台变更执行）。
