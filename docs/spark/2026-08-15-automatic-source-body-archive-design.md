# WeMediaBuddy 情报正文自动归档设计

日期：2026-08-15  
状态：Owner 已批准设计，待实现  
范围：情报来源入库后的正文自动归档、历史补抓、失败诊断与统一重试

## 1. 问题

当前情报渠道只保证 `Source` 来源记录入库。正文抓取由资料详情中的手动按钮触发，因此大量资料只有标题、摘要和原文 URL，`source_body_cache` 长期不存在或停留在失败/空正文状态。媒体归档已经具备持久任务、恢复和重试能力，但正文没有同等保证。

这造成三个直接问题：

1. 用户看到“资料已入库”时，无法判断正文是否真正保存；
2. Pi、知识编译和后续创作经常只能使用摘要；
3. 抓取失败分散在单条资料中，无法统一分析、修复和重试。

## 2. 产品决定

1. 所有新入库情报都必须自动进入正文归档流程，不以价值判断、是否进入选题池或用户打开详情为前提。
2. Source 保存不等待网络抓取；正文归档在持久后台任务中执行。
3. 来源入库失败与正文归档失败是两个独立结果。正文失败不得回滚已经保存的 Source、媒体候选或本轮情报扫描。
4. 结构化渠道已经提供完整文本时，直接固化该文本，不重复访问原网页；只有缺少完整文本时才根据原文 URL 抓取。
5. 自动抓取最多尝试 3 次，采用退避策略。三次均失败后进入统一异常中心，不再无限自动请求。
6. 历史缺失正文的资料按时间倒序、限速分批补抓；新资料永远优先。
7. 正文抓取和 Pi 上下文彻底解耦。加入 Pi 不触发抓取，正文抓取也不自动加入 Pi。

## 3. 成功定义

- 每条有完整渠道文本或可抓取 URL 的新 Source，在入库后自动得到持久正文任务。
- 应用退出、崩溃或重启不会丢失待执行任务。
- 相同 `sourceId + sourceRevision` 重放不会重复抓取或创建重复正文版本。
- X 等结构化渠道的完整帖子文本直接进入正文版本，不重复请求 X 页面。
- 普通网页经过安全下载和正文提取后写入现有正文真源。
- 三次失败后，用户可以在一个统一页面看到失败原因、聚合规律和可执行的重试动作。
- 历史补抓不会阻塞或明显拖慢当天情报扫描。

## 4. 非目标

- 不自动绕过登录、验证码、付费墙或站点访问限制。
- 不自动放宽 SSRF、私网访问、内容大小或 MIME 安全限制。
- 不让 AI 自动修改抓取器代码、站点适配器或安全策略。
- 不把摘要冒充正文。
- 不改变人工最终发布边界。
- 不为正文建立第二套真源；`source_body_revisions` 仍是不变历史，`source_body_cache` 仍是最新投影。

## 5. 总体流程

```text
渠道采集
  ↓
Source + 正文任务登记（同一持久化边界）
  ↓ 提交成功
后台正文 Worker
  ├─ 有可信完整文本 → 直接固化
  ├─ 有原文 URL → 安全下载 → 正文提取 → 固化
  └─ 两者皆无 → 标记 unavailable
  ↓
source_body_revisions（不可变正文版本）
  ↓
source_body_cache（最新投影）
  ↓
搜索索引 / Pi / 知识编译消费
```

正文 Worker 不参与 Source 保存事务中的网络 I/O。事务内只保存 Source、正文输入和持久任务；网络请求必须在提交后执行。

## 6. 统一入库边界

当前正式渠道既有 `dispatchSourceUpsertBatch`，也有直接调用 `upsertSource` 的路径。实现时必须完成干净切换：所有正式情报入库路径共享同一个“保存 Source 并登记正文任务”的持久化入口，不允许某些渠道靠调用方记得补调度。

该入口需要接收可选的明确正文候选：

```ts
type SourceBodyCandidate = {
  kind: 'full_text';
  text: string;
  contentType: string;
  origin: string;
};
```

只有渠道明确声明为完整文本的内容才能传入 `full_text`。普通 `summary` 不自动升级为正文。

任务幂等键固定为：

```text
source:<sourceId>:r<sourceRevision>
```

同一 revision 重放时：

- 已有 `ready` 正文：不创建任务；
- 已有未完成任务：复用原任务；
- 已有终态失败：保持终态，除非发生人工重试；
- Source 实质变化并产生新 revision：创建新任务。

## 7. 正文取得规则

按以下优先级执行：

1. **完整渠道文本**：直接清洗并固化。适用于 X 帖子、渠道返回的完整公告正文、研究工具已读取的完整页面文本。
2. **原文 URL**：走统一安全网页读取器，提取可读正文。
3. **无正文来源**：没有完整文本且没有 URL 时，任务终态为 `unavailable`，原因码为 `NO_BODY_SOURCE`。

正文提取结果为空时不得使用摘要填充正文。摘要仍保留在 Source 中，消费方可以明确以 `summary` 兜底。

## 8. 持久任务模型

正文任务至少包含：

- `id`
- `workspaceId`
- `sourceId`
- `sourceRevision`
- `jobKey`
- `priority`：`new_source` 或 `historical_backfill`
- `status`
- `attemptCount`
- `nextAttemptAt`
- `bodyCandidate`（如有，持久化冻结）
- `lastErrorCode`
- `lastErrorMessage`
- `createdAt`
- `updatedAt`
- `finishedAt`

状态机：

```text
pending → running → ready
                  ↘ retry_wait → running
                  ↘ needs_review
                  ↘ unavailable
```

恢复规则：

- 冷启动恢复 `pending`；
- 超过租约时间的 `running` 回收为 `pending`；
- 到期的 `retry_wait` 恢复执行；
- `ready`、`needs_review`、`unavailable` 不自动重放。

Worker 必须有界并发、可暂停、可恢复，并优先处理 `new_source`。历史补抓不能饿死，但只能使用剩余并发与限速额度。

## 9. 重试策略

一次自动周期最多 3 次实际尝试。建议退避：

- 第 1 次失败后：短间隔重试；
- 第 2 次失败后：较长间隔重试；
- 第 3 次失败后：进入 `needs_review`。

退避时间允许加入小幅抖动，避免同一域名任务同时重放。`Retry-After` 存在时必须遵守，且不得早于系统退避下限。

以下原因默认不可自动重试，首次确认后直接进入人工处理或 `unavailable`：

- `NO_BODY_SOURCE`
- `URL_SECURITY_BLOCKED`
- 明确的 404/410
- 明确需要登录、验证码或付费授权
- 版权或渠道策略禁止抓取

人工从异常中心发起重试时创建新的重试周期，仍然最多 3 次并继续受全局及域名限速约束。

## 10. 安全抓取要求

自动正文抓取不能直接扩大现有简单 `fetch` 的风险。URL 抓取必须统一具备：

- 仅允许 HTTP/HTTPS；
- 拒绝环回、私网、链路本地和保留地址；
- 首次解析及每次重定向均执行 DNS/IP 校验，防止 DNS 重绑定；
- 逐跳限制重定向次数；
- 请求超时和流式中止；
- 响应字节上限；
- Content-Type 白名单；
- 文本解码与正文字符上限；
- 不执行网页脚本；
- 动态渲染仅能使用现有受控公开网页读取能力，并由渠道或失败分类明确允许。

安全拦截不是普通网络失败，不能通过“重试全部”绕过。

## 11. 失败诊断

每次尝试必须记录结构化诊断，至少包括：

- `errorCode`
- HTTP 状态码（如有）
- 请求 URL、最终 URL和重定向链摘要
- 域名与来源渠道
- 抓取方式：`channel_text`、`static_http` 或受控动态读取
- Content-Type
- 已读取字节数
- 是否识别为登录墙、验证码、限流或动态空页面
- 提取器名称与版本
- 提取字符数
- 尝试序号、开始和结束时间
- 下一次允许重试时间

错误信息必须去除凭据、Cookie、授权头和敏感查询参数。原始响应正文不作为诊断日志永久保存。

标准原因码至少覆盖：

- `HTTP_UNAUTHORIZED`
- `HTTP_FORBIDDEN`
- `HTTP_NOT_FOUND`
- `HTTP_GONE`
- `HTTP_RATE_LIMITED`
- `NETWORK_TIMEOUT`
- `NETWORK_ERROR`
- `LOGIN_REQUIRED`
- `CAPTCHA_DETECTED`
- `DYNAMIC_PAGE_EMPTY`
- `EXTRACTION_EMPTY`
- `CONTENT_TYPE_UNSUPPORTED`
- `RESPONSE_TOO_LARGE`
- `URL_INVALID`
- `URL_SECURITY_BLOCKED`
- `NO_BODY_SOURCE`
- `UNKNOWN_ERROR`

## 12. 统一异常中心

入口固定为：

```text
资料库 → 采集异常
```

它是资料库内部视图，不新增顶级导航。

默认按“原因码 → 域名 → 渠道”聚合，展示：

- 失败资料数量；
- 最近失败时间；
- 最近错误摘要；
- 三次尝试时间线；
- 系统判断的可能原因；
- 推荐处理方式；
- 当前是否允许重试。

支持：

1. `重试所选资料`
2. `重试这一类失败`
3. `重试全部当前可重试项`

“重试全部”必须排除安全拦截、明确失效链接、登录/验证码/授权限制和政策禁止项。每次批量操作先显示实际可重试数量及排除数量；执行后仍受后台队列、域名限速和三次上限控制。

异常中心用于发现系统性问题。例如同一域名大量出现 `DYNAMIC_PAGE_EMPTY` 时，可以修复该站点适配器，再按原因组批量重试。系统可以归类和提出建议，但不得自动修改代码或安全策略。

## 13. 历史补抓

首次启用时扫描所有非归档 Source：

- 没有 `ready` 正文版本的资料进入候选；
- 已有成功正文的不重复抓；
- 现有 `failed`/`empty` 缓存允许进入一次历史补抓周期；
- 按 `collectedAt`/创建时间倒序；
- 任务优先级为 `historical_backfill`；
- 分页登记，避免一次事务装载全部历史记录；
- 进度水位持久化，应用重启后续跑；
- 新来源任务始终优先；
- 全局暂停正文归档时，历史与新增任务一并暂停，但已经提交的 Source 不受影响。

历史补抓完成后保留统计：总候选数、成功数、无需处理数、`needs_review` 数和 `unavailable` 数。

## 14. UI 调整

自动归档上线后，来源详情不再把“抓取正文”当作日常主操作。

正文区域仅显示真实状态：

- `正文归档中`
- `正文已保存 · N 字`
- `等待重试 · 2/3`
- `正文归档失败`
- `缺少正文来源`

只有 `needs_review`、`unavailable` 或明确需要人工刷新时才显示次级动作：

- `查看失败原因`
- `重新抓取`

Pi 操作只保留加入/移出上下文。Pi 消费规则：

- `ready` 且正文非空：使用正文摘录；
- 其他状态：明确标记为摘要兜底；
- 不因加入 Pi 而改变正文任务状态。

## 15. 与现有系统的关系

- 复用 `source_body_cache` 最新投影；
- 复用 `source_body_revisions` 不可变历史；
- 正文成功后继续触发现有搜索索引投影；
- 知识编译需要消费相同 Source revision 对应的正文。若编译先于正文完成，可使用摘要完成初始编译；正文版本落地后必须通过现有受控增量机制触发该 Source 的重新评估，不能静默永久停留在摘要版本；
- 媒体归档与正文归档相互独立，共享 Source revision 身份，但不互相阻塞；
- 删除 Source 时，按现有生命周期清理其正文任务、最新缓存和授权范围内的历史；
- 数据根目录和工作空间隔离必须与现有 Source、媒体和任务运行时一致。

## 16. 可观察性

“今日”运行结果需要给出正文归档摘要，但不等待全部任务结束：

- 本轮新登记正文任务数；
- 已直接固化完整渠道文本数；
- 已排队网页抓取数；
- 当前失败或需要处理数。

资料库提供全局队列与异常统计。状态文案必须区分：

- Source 已入库；
- 正文已排队；
- 正文已保存；
- 正文归档失败。

不得再用“资料已入库”暗示正文已经保存。

## 17. 验收标准

### 17.1 入库覆盖

- X Lists、官方网页、Research、Pi/MCP 来源写入及其他正式 Source 入库路径均产生正文结果或持久任务。
- 不存在仍可绕过正文调度的正式 `upsertSource` 调用路径。

### 17.2 正文结果

- 结构化完整文本直接生成 `ready` 正文，不发生网页请求。
- 网页来源经安全读取后生成 `source_body_revisions` 和 `source_body_cache`。
- 摘要不会被误写为正文。

### 17.3 可靠性

- Source 提交成功后正文抓取失败，Source 仍可读。
- 应用在 `pending`、`running`、`retry_wait` 任一阶段退出后，重启能够恢复。
- 相同 job key 并发或重放只得到一个有效任务和一个相同正文版本。
- 三次失败后停止自动请求并进入 `needs_review`。

### 17.4 安全

- 私网、环回、DNS 重绑定、危险重定向、超限响应和非法 Content-Type 被拒绝。
- 安全拒绝无法通过批量重试绕过。
- 诊断记录不泄露凭据和敏感请求信息。

### 17.5 历史补抓

- 新任务优先于历史任务；历史任务仍能持续前进。
- 历史水位可恢复；重复启动不会重复登记相同 revision。
- 已有成功正文不被无意义重抓。

### 17.6 异常中心

- 能按原因、域名和渠道聚合三次失败任务；
- 能查看单条三次尝试记录；
- 能重试所选、同类和全部可重试项；
- 不可重试项有明确原因且不会进入批量请求；
- 修复提取器后可对对应失败组发起新的受限重试周期。

### 17.7 真实产品验证

真实 Electron 中完成以下场景：

1. 扫描新 X 来源，正文自动出现且未请求 X 原页；
2. 扫描普通网页来源，Source 先出现，正文随后自动变为已保存；
3. 模拟连续失败三次，来源保留且异常中心出现聚合记录；
4. 修复失败条件后按组重试，正文成功且异常计数下降；
5. 执行历史补抓时新入库来源仍优先完成；
6. 中途退出应用并重启，队列继续执行；
7. Pi 加入/移出来源不会触发额外正文抓取。

## 18. 实现边界

本设计预计涉及 Source 统一写入口、正文任务持久化与 Worker、历史补抓、结构化诊断、资料库异常视图、Today/详情状态文案和聚焦验证。实现计划必须先枚举全部正式 Source 写入调用点，并以“无绕过路径”为干净切换完成条件。
