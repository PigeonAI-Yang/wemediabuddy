# 工作空间情报渠道模块设计

日期：2026-08-03

状态：Owner 已确认并授权实施

范围：WeMediaBuddy 工作空间的情报来源配置、扫描编排、运行回执与用户授权

## 1. 问题

当前工作空间已经能选择不同 `intelligencePack`，但“空间如何获得真实情报能力”没有形成用户可理解的闭环：

- 官网名单和采集方法藏在不同赛道 Skill 的 `source-map` / `source-index` 中；
- X Lists 是独立业务能力，却需要用户自行找到分散的浏览器、登录和绑定入口；
- 工作空间配方声明“允许使用什么”，没有说明“当前配置了什么、是否可运行”；
- 每日任务可能在所有发现渠道不可用时仍启动 Pi，最后以“至少一条资料落库”失败；
- 同一套采集流程被按 AI、英国生活、游戏资讯重复包装，赛道差异与渠道差异混在一起。

Owner 明确的第一性原理是：所有工作空间使用相同工作流，从少数固定类型的渠道取得信息；空间之间真正变化的是网站、X Lists、受众和编辑目标，而不是采集流程本身。

## 2. 目标

把情报能力拆成两层：

1. 安装内固定复用的渠道模块，负责“如何读取一种渠道”；
2. 每个 data-root 独立保存的来源配置，负责“当前工作空间读取哪些来源”。

首版只交付：

- 官网模块；
- X Lists 模块；
- 一套共享的今日情报编排；
- 当前工作空间的渠道管理、就绪状态、运行选择和逐来源回执。

## 3. 非目标

- 不建设第三方插件市场、模块安装器、权限沙箱或兼容层；
- 不在首版加入 X 单账号、小红书、Reddit、论坛或其他社区模块；
- 不改变安装级共享的 Pi API/model 预设；
- 不共享不同工作空间的账号、登录态、来源配置、缓存、回执或资料；
- 不新建第二套资料库；采集结果继续进入现有 `source_feeds` / `source_items`；
- 不处理截图中 Pi 恢复已删除临时工作目录的问题，该问题作为独立 BUG 追踪。

## 4. 核心模型

### 4.1 渠道模块

渠道模块是 WMB 编译期固定能力，不是赛道 Skill，也不是可安装插件。

首版只有两个模块：

| 模块 | 接受输入 | 解析后的稳定身份 | 运行职责 |
| --- | --- | --- | --- |
| 官网 | 网站名称、首页 URL、新闻页或栏目 URL | 规范内容入口 URL | 识别可采集入口、真实试读、发现新内容 |
| X Lists | List 名称、URL 或 List ID | 当前根账号 + List ID | 从当前账号可访问的 Lists 中匹配、读取有界动态 |

模块不知道工作空间属于 AI、英国生活还是游戏资讯。模块只负责解析、试读、扫描和返回统一回执。

### 4.2 工作空间来源配置

每个 data-root 独立保存：

- 使用的渠道模块；
- 用户原始输入；
- 模块解析出的真实身份；
- 显示名称和规范 URL；
- 启用状态；
- 解析/试读状态与最近错误；
- revision；
- 对 X Lists 而言，当前根账号和既有 binding；
- 最近扫描回执与该来源产生的资料关系。

现有 `source_feeds` 继续表示长期来源，`source_items` 继续表示文章、帖子等单条资料。官网来源直接使用规范 URL 作为稳定身份；X Lists 继续复用现有 `x_list_bindings → source_feed_id` 关系，不复制 List 身份或另建平行资料模型。

### 4.3 共享情报流程

AI、英国生活和未来赛道不再各自拥有一套采集 Skill。共享流程是：

```text
读取当前工作空间配置
→ 运行本次选中的全部已启用渠道模块
→ 标准化候选资料
→ 跨渠道去重与合并
→ 对具体事实按需要补充核验
→ 结合当前 workspace audience/contentGoal/editorialBrief 判断内容机会
→ 写入现有资料、机会和方案对象
```

官网和 X Lists 在发现阶段地位相同。官网不是每日必然产生内容的高优先级渠道；它只是在候选内容涉及政策、规则、价格等事实时，可能承担核验角色。

工作空间差异来自来源配置、受众和编辑目标，不来自复制的采集代码。

## 5. 用户体验

### 5.1 页面归属

- `设置 → AI 与模型`：继续管理安装级共享 Pi 预设；
- `设置 → 浏览器与账号`：继续管理当前根的底层浏览器和登录环境；
- `发现 → 情报渠道`：新增当前工作空间的渠道管理入口；
- `今日 → 开始今日情报`：展示本次实际运行的模块和来源数量。

“设置”回答系统是否具备底层环境；“情报渠道”回答当前空间到底关注什么。

### 5.2 情报渠道页

页面显示两个固定模块卡片：官网、X Lists。每张卡片显示：

- 当前状态：已就绪、需要配置、需要登录、部分异常；
- 已启用来源数量；
- 最近检查时间和结果摘要；
- 管理来源入口；
- 立即试扫入口。

模块卡片不是安装按钮。两个模块随 WMB 提供；用户管理的是模块下的来源实例。

### 5.3 添加官网

用户可以输入任意公开网站的名称或 URL，不受预置目录限制：

1. 官网模块解析规范站点和实际更新入口；
2. 对入口执行真实试读；
3. 展示网站名称、规范 URL、找到的内容入口和试读结果；
4. 用户确认后加入当前工作空间并启用。

同一规范 URL 不能重复加入。动态渲染、登录墙、反自动化或无法提取标题/日期/原文链接的网站必须显示准确原因，不得显示为已就绪。

官方工作空间模板可以附带初始官网来源，但创建确认页必须展示完整来源清单。模板只是初始推荐，不是永久白名单；用户可继续新增、停用或移除网站。

### 5.4 添加 X List

用户可以输入 List 名称、URL 或 ID：

1. 缺少当前根 X 登录态时直接要求登录；
2. 从当前账号实际可访问的 Lists 中解析匹配；
3. 名称重合时展示所属账号、名称、List ID 和规范 URL；
4. 用户选择并确认后复用现有 binding 接入发现。

List 名称仅用于搜索，不作为身份。换账号、换工作空间或 List 身份变化必须重新验证，不得借用其他根的登录态、缓存或 binding。

### 5.5 来源管理与 AI 授权

官网和 X Lists 统一提供：

- 启用：参加默认今日扫描；
- 停用：保留配置和历史资料，但不参加默认扫描；
- 立即试扫：产生真实运行回执；
- 移除：停止关注，不删除已经入库的历史资料。

用户、内置 Pi 和外部 Agent 使用同一业务命令。AI 可以识别来源、试读并准备新增/停用/启用/移除的精确变更清单；只有用户确认后才能执行。

一次确认可以覆盖一组精确来源。确认必须绑定：

- workspace ID 和 profile revision；
- 变更类型；
- 每个来源的渠道模块和稳定身份；
- 展示给用户的完整 diff。

任一绑定发生变化即使旧确认失效。不存在会话级或长期的来源管理授权。

### 5.6 启动今日情报

点击“开始今日情报”时：

- 默认选中当前空间全部已启用模块及其来源；
- 显示每个模块的来源数量和就绪状态；
- 用户可仅对本次运行临时取消模块，不改变长期配置；
- 能在启动前确定的缺模型、缺登录、零启用来源等阻塞直接显示，不启动 Pi；
- 至少存在一个可运行来源时启动共享情报流程。

## 6. 运行回执与完成语义

每个参与运行的来源必须产生一条真实回执，最少包含：

- task ID、workspace ID、source feed/binding 身份；
- 渠道模块；
- `checked_at`；
- 状态；
- 候选数量、保存数量；
- 错误 code 和 message。

最小状态语义：

| 结果 | 定义 |
| --- | --- |
| succeeded | 至少一个来源被真实检查；允许 0 条更新、0 条资料、0 个机会和空方案 |
| partial | 至少一个来源检查成功，同时有其他来源失败或需要用户处理 |
| needs_user | 所有本次可选来源均被登录、账号或配置阻塞；可预检时不启动 Pi |
| failed | 编排或运行时失败，未形成任何可信来源检查回执 |

“今天没有新内容”是有效业务结果，不是失败。成功门验证真实扫描回执，不再验证“至少一条资料落库”或“方案至少一项”。不得为满足成功门而生成假资料或占位方案。

## 7. 数据流和并发

一次今日情报任务冻结当前 workspace/profile revision、本次模块选择和来源 revision。随后：

1. 官网和 X Lists 按来源执行有界扫描；互不依赖的读取可以并发；
2. 每个来源独立写回回执；
3. 候选内容标准化后进入现有资料写入和 URL/fingerprint 去重；
4. 资料写入完成后运行统一机会判断；
5. 汇总逐来源结果得到任务最终状态；
6. 切换工作空间、账号或来源 revision 变化时，迟到结果不得写入新状态。

扫描一个来源失败不回滚其他来源的成功资料。工作空间切换继续遵守现有排空和重启协议。

## 8. 错误处理

- 任意网站解析失败：来源保持未启用或异常状态，返回实际原因；
- 网站检查成功但无变化：记录 `0` 候选的成功回执；
- X 未登录：该来源 `needs_user`，不得建立 binding 或写缓存；
- X List 名称重合：要求用户选择，不猜测；
- X 账号变化：现有稳定身份重新验证，旧确认失效；
- 单个来源暂时不可访问：本次该来源失败，其他来源继续；
- 所有来源都不可运行：预检返回 `needs_user`，不启动 Pi；
- Pi 或编排进程崩溃且无可信回执：任务失败；已有回执和已提交资料保留。

## 9. 验收标准

1. 新建英国生活空间时，创建确认页展示并可确认模板附带的全部官网来源。
2. 用户可输入任意公开网站名称或 URL；真实识别和试读成功后才能启用。
3. 同一规范 URL 不重复添加；无法读取的网站展示准确原因。
4. 用户可输入 X List 名称、URL 或 ID；重名时展示真实账号和 List ID 供选择。
5. X List 始终使用当前工作空间账号，不跨空间复用登录态。
6. 今日情报默认运行全部已启用模块，也允许本次临时取消模块。
7. 每个参与来源产生真实回执；0 条更新可以成功并允许空方案。
8. 部分来源失败时保留成功结果；全部被配置或登录阻塞时启动前进入 `needs_user`。
9. AI 可准备精确增删清单，用户确认后执行；变化后的工作空间拒绝旧确认且零写入。
10. AI 与英国空间配置相同名称、URL 或 List 时，配置、回执和资料完全隔离。
11. 模型/API 预设保持安装级共享，不进入渠道模块或 data-root 配置。
12. 首版只有官网和 X Lists 两个固定模块，产品不出现插件安装、第三方模块或自由工作流入口。

## 10. 最小验证

- 单元检查：官网规范 URL 去重；X List 名称解析与重名拒绝；确认绑定 stale 拒绝；任务状态聚合四种结果。
- 集成检查：两个模块各产生逐来源回执，并通过现有 `source_feeds/source_items` 落库和去重。
- 负向检查：零更新成功；全部登录阻塞不启动 Pi；一个来源失败不丢失其他来源结果；跨根相同 fixture 零串线。
- 真实桌面验收：在 AI 与英国生活两个真实根分别新增官网和同名 X List，冷切换后读回各自配置；英国生活运行一次包含 0 更新官网和有动态 X List 的今日情报，最终为 succeeded/partial 而不是“至少一条资料落库”失败。

## 11. 实施边界

本设计作为 M-2100 单独进入 PRD/SPEC/TECHNICAL_DESIGN 和权威 `TASKS.md`，按依赖有序任务链实施。不得把它作为当前 Pi 报错的局部 UI 补丁；截图中的 Pi 临时工作目录错误仍由独立 BUG 处理。
